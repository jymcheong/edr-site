Why Attackers Kill ETW Before They Do Anything Else

Event Tracing for Windows is the most powerful telemetry source on a Windows endpoint. Which is exactly why attackers disable it first.

What ETW Is and Why It Matters

Event Tracing for Windows (ETW) is a kernel-level tracing framework built into Windows. It provides structured telemetry from the operating system itself: process creation, DLL loads, network connections, file system operations, registry changes, and much more. Sysmon, Windows Defender, and most commercial EDR products consume ETW sessions under the hood.

That dependency is the problem. If an attacker can silence or distort an ETW provider, they can operate with reduced visibility — even on an endpoint that looks fully instrumented from the outside.

The Five ETW-Silencing Techniques

# Technique 1 — Stop the trace session directly
sc stop Sysmon64
# Technique 2 — Patch the EtwpNotifyConsumer function in ntdll
WriteProcessMemory() → NOP the dispatch path

1. Stopping the trace session. The simplest method: stop Sysmon, Windows Defender, or any ETW consumer as a service. Detectable via Service Control Manager events (7036) and Sysmon's own process-terminated log — if you still have a copy.

2. Patching ntdll in-process. Malware patches the ETW dispatch path inside ntdll.dll within the target process. The kernel still raises events, but the consuming thread never sees them. Ghidra's EvasionScan script detects the stub pattern statically; Frida catches it dynamically.

3. NtTraceControl / EtwpStopTrace. Direct syscall to the kernel's trace control interface, bypassing ntdll entirely. Evades userland hooks. Requires elevated privileges but not SYSTEM — a medium-integrity process with SeDebugPrivilege is enough.

4. Stomping the session buffer. Corrupt the EVENT_TRACE_LOGFILE buffer so consumers receive garbage instead of valid events. Logs appear active; events are unreadable. Detection: checksum comparison across consecutive reads.

5. Provider deregistration injection. Inject into a process that holds an ETW provider handle and call EtwUnregister() on the provider's REGHANDLE. That provider goes silent for the lifetime of that process.

What Actually Detects These

Technique Detection Source Reliability
Stop service SCM event 7036, WMI High
ntdll patch Ghidra EvasionScan, Frida hook Medium
NtTraceControl syscall ETW-Ti, kernel audit Medium
Buffer stomp Custom consumer checksum Low (rarely implemented)
Provider deregistration ETW session heartbeat diff Low (rarely implemented)

Defensive Posture

Three controls that actually move the needle:

  1. Run a secondary ETW consumer on a separate process. If your primary consumer is silenced, a second consumer on a separate session still sees events. Attackers rarely know to kill both unless they've done recon on your stack.
  2. Alert on session gap — not just session stop. A session that disappears is obvious. A session that silently stops producing events is not. Set a heartbeat: if the expected event rate drops below threshold for 60 seconds, that's an incident.
  3. Protect Sysmon with a WFP driver or minifilter. Stops service-stop without admin access. Doesn't stop kernel-level attacks, but raises the privilege bar significantly.

The honest summary: ETW silencing is not exotic. It shows up in commodity crimeware, not just nation-state toolkits. If your detection stack relies on a single ETW session with no heartbeat monitoring, assume the gap exists and plan accordingly.
